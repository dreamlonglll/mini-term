# Spec：移动端远程驱动体系 v1（含 cc-connect 移除）

> 状态：ready-for-agent · 定稿 2026-07-24
> 决策背景：`docs/adr/0001-replace-cc-connect-with-mobile-relay.md` · 术语：根目录 `CONTEXT.md`

## Problem Statement

我在电脑上用 mini-term 同时跑着多个 Claude / Codex agent。人离开电脑后（吃饭、通勤、睡前），我完全失去对这些 agent 的感知和控制：不知道哪个干完了、干得对不对，也没法在它空闲时把下一条指令交代下去，只能回到电脑前处理。现有的 cc-connect 集成虽然提供了 IM 远程驱动，但它依赖第三方进程、IM 平台配置和它自己的会话模型，AI 交互不在 mini-term 的终端里发生，与"mini-term 是 AI 交互唯一现场"的定位相悖，配置链路也过长。

## Solution

移除 cc-connect 集成，替换为 mini-term 原生的三件套：

1. **中转服务器**（自托管，Docker 一键部署）——桌面端主动出站长连穿 NAT，移动端连同一台中转，中转只做转发；
2. **移动端**（PWA，由中转托管，扫码即用）——展示所有活跃 AI 会话的项目/pane 及状态，点进任一 pane 看**对话镜像**：桌面输入、移动端指令、AI 回复实时混排的聊天流；
3. **移动端指令**——在手机聊天框输入，经中转送达桌面端后直接写入目标 pane 的 PTY，等价于本人在桌面敲键盘。

AI 交互始终只发生在 mini-term 桌面端的终端里；移动端只收发消息，永远不直接接触 AI 进程或 PTY。

## User Stories

### 配对与连接

1. 作为 mini-term 用户，我想在桌面端设置里填入自己中转服务器的地址，以便桌面端与我的中转建立出站长连。
2. 作为 mini-term 用户，我想在桌面端看到与中转的连接状态（已连接 / 断开 / 重连中），以便判断远程通道是否可用。
3. 作为 mini-term 用户，我想桌面端断线后自动指数退避重连，以便网络恢复后远程通道自动复活、无需手动干预。
4. 作为 mini-term 用户，我想在桌面端生成一张包含中转地址和一次性配对码的二维码，以便手机扫码完成配对而无需手动输入任何内容。
5. 作为移动端用户，我想扫码后自动完成配对并直接进入应用，以便零输入开始使用。
6. 作为移动端用户，我想配对成功后获得长期凭证并自动重连，以便下次打开 PWA 无需重新扫码。
7. 作为 mini-term 用户，我想新手机扫码配对时自动顶替旧手机的凭证（1×1 拓扑），以便换机后旧设备立即失效。
8. 作为 mini-term 用户，我想在桌面端一键重置配对，以便手机丢失时立刻吊销移动端访问。

### 浏览与对话镜像

9. 作为移动端用户，我想看到所有存在活跃 AI 会话的项目及其 pane 列表（含 ai-working / ai-idle / error 状态），以便一眼掌握各 agent 的忙闲。
10. 作为移动端用户，我想该列表实时反映状态变化与 AI 会话的出现/消失，以便无需手动刷新。
11. 作为移动端用户，我想点进某个 pane 查看对话镜像，以便了解这个 agent 正在做什么、做到哪一步。
12. 作为移动端用户，我想桌面端在终端里敲入的 prompt 也实时出现在对话镜像中，以便手机上的视角与桌面完全一致。
13. 作为移动端用户，我想 AI 回复以渲染后的 Markdown 展示，以便在手机上舒适阅读代码块和列表。
14. 作为移动端用户，我想打开对话时先看到最近的历史消息，上拉可加载更早的，以便快速回顾上下文。
15. 作为移动端用户，我想每条消息清晰标注来源（桌面输入 / 移动端指令 / AI 回复），以便理解对话流。
16. 作为移动端用户，我想在项目与 pane 之间自由切换，以便逐个巡视多个并行的 agent。

### 发送移动端指令

17. 作为移动端用户，我想在对话镜像底部的输入框发送移动端指令，以便远程驱动该 pane 的 AI。
18. 作为移动端用户，我想发送后立刻收到"已写入桌面终端"的回执，以便确认指令送达（不做排队状态，写穿即回执）。
19. 作为移动端用户，我想我的指令随后经会话记录回流出现在对话镜像里，以便确认 AI 真正接收了它。
20. 作为桌面端用户，我想移动端发来的指令原样出现在对应终端中（等价本人敲键盘 + 回车），以便桌面侧对远程操作完全透明。

### 离线与异常

21. 作为移动端用户，我想桌面端离线时看到明确的离线横幅且发送框置灰，以便不产生"指令已发出"的错觉（离线即拒，不存储转发）。
22. 作为移动端用户，我想目标 pane 的 AI 会话结束或 pane 关闭时收到明确提示并回到列表，以便不对已消失的目标盲发。
23. 作为移动端用户，我想手机网络抖动后 PWA 自动重连并恢复订阅，以便地铁/电梯场景无需手动刷新。
24. 作为移动端用户，我想凭证已被顶替（换过新手机）时收到"配对已失效，请重新扫码"的明确提示，以便理解为何连不上。

### 安全

25. 作为自托管运维者，我想中转对消息体不落盘、日志不含明文对话，以便服务器被入侵时不泄露任何历史对话。
26. 作为 mini-term 用户，我想全链路走 TLS（wss/https），以便公网传输不被窃听。
27. 作为 mini-term 用户，我想无凭证或凭证失效的连接被中转直接拒绝，以便陌生人无法窥探或注入。
28. 作为 mini-term 用户，我想裸 shell pane 对移动端完全不可见、不可驱动，以便远程能力永远限定在 AI 会话内，不构成远程任意命令执行。

### 部署与使用门槛

29. 作为自托管运维者，我想用 Docker 一条命令跑起中转（镜像内含 PWA 静态资源），以便部署门槛最低。
30. 作为自托管运维者，我想通过环境变量配置端口与 TLS/反代适配，以便接入自己的证书体系。
31. 作为移动端用户，我想把 PWA 添加到主屏幕并以独立窗口打开，以便获得接近原生应用的使用体验。
32. 作为移动端用户，我想 PWA 界面支持中英双语，以便与桌面端语言体验一致。

### cc-connect 移除

33. 作为 mini-term 用户，我想升级后不再看到 cc-connect 的任何入口与配置项，以便界面没有废弃功能残留。
34. 作为 mini-term 老用户，我想带 `ccConnect` 字段的旧 config.json 正常加载不报错、下次保存自动清除该字段，以便升级完全无感。
35. 作为 mini-term 用户，我想在 release notes 里读到 cc-connect 被移除的原因与替代方案，以便理解这次变更。

## Implementation Decisions

**交付分两个独立阶段**（既定共识，不可合并交付）：

### Phase 0 — cc-connect 移除（独立 commit，先行发版）

- 删除 cc-connect 后端模块及其全部 Tauri command、前端弹窗/仪表盘/探测 hook、store 分片、i18n 字典与顶栏入口。
- AppConfig 删除 ccConnect 字段；依赖 serde 对未知字段的默认忽略实现旧配置零迁移。
- 评估并移除仅为 cc-connect 引入的依赖（HTTP 客户端库）；toml_edit 因 SSH MCP 注册仍在使用，保留。
- release notes 说明移除原因并预告移动端体系。

### Phase 1 — 移动端 + 中转 v1

- **仓库形态**：monorepo 新增两个顶层目录——中转服务（Rust axum + tokio，含 Dockerfile）与移动端 PWA（React + TypeScript + Vite，构建产物打入中转镜像由其托管）。
- **协议**：JSON over WebSocket。消息类型定义在桌面端与中转共享的 Rust crate 中；PWA 侧 TypeScript 类型按仓库既有 serde camelCase 对齐约定手写镜像。
- **桌面端归属**：对中转的出站 WSS 长连由 Rust 后端持有（指数退避重连）；前端 store 将活跃 AI 会话的结构与状态变更经 command 喂给后端；对话镜像消息由后端基于会话记录文件的增量解析生成（复用既有的会话解析与文件监听能力），不读终端原始输出。
- **指令通路**：中转 → 桌面后端 → 直接写入目标 pane 的 PTY（复用既有写入通道），随即向移动端发"已写入"回执。无排队状态机；AI 工作中依赖 CLI 自身输入缓冲。
- **配对流程**：桌面端向中转注册并获取一次性配对码 → 桌面端展示二维码（中转地址 + 配对码）→ 移动端扫码兑换长期凭证。新配对生效即吊销旧凭证（1×1）。桌面端可主动重置全部配对。
- **在线状态**：中转追踪桌面端连接存活并向移动端推送 presence 事件；桌面离线时中转直接拒绝移动端指令。可选实现短暂断线宽限期（约 30 秒）平滑网络抖动，不做持久化暂存。
- **镜像历史深度**：打开对话默认取最近 50 条，上拉分页加载更早，由桌面端按需从会话记录读取。
- **中转纪律**：消息体仅内存转发，不落盘；日志只记元数据（连接、鉴权结果），不记消息内容。
- **可见性规则**：仅处于 AI 会话中的 pane（ai-working / ai-idle 及 error 态的 AI pane）进入移动端结构快照；裸 shell pane 一律不出现。
- **UI 落位**：顶栏原 Connect 入口位置由"移动端"入口取代（配对二维码、中转连接状态、重置配对）；桌面新界面接入既有 i18n 双语系统；PWA 内置同模式的轻量双语字典。
- **术语纪律**：全部命名遵循 CONTEXT.md——移动端 / 中转服务器 / 配对 / 对话镜像 / 移动端指令；"远程"一词保留给 SSH 语境。

## Testing Decisions

好的测试只测外部行为，不测内部实现。本 spec 两条 seam（已与维护者确认）：

**Seam 1（新增）：中转服务器的协议边界。** 进程内启动中转实例，用模拟的桌面端 WS 客户端与移动端 WS 客户端从两头驱动真实协议帧。覆盖：配对码兑换凭证、错误/过期凭证拒绝、新配对顶替旧凭证、双向消息路由、presence 推送与离线即拒、消息体不落盘（测试后检查无残留文件）。中转的一切行为从这条边界验证，不直接测其内部模块。

**Seam 2（既有）：桌面端 cargo 单元测试。** 沿用仓库现有 334 个 Rust 单测的模式与位置，测桌面端纯逻辑：
- config 往返——新增中转配置字段的序列化往返；含 `ccConnect` 字段的旧配置静默兼容（Phase 0 即需覆盖）。先例：config 版本迁移与 sshGroups round-trip 单测。
- 会话记录增量解析 → 对话镜像消息序列（来源标注、增量边界）。先例：既有会话解析测试。
- 协议消息 serde camelCase 往返。先例：既有跨边界类型对齐测试。

**不开自动化缝**：桌面前端与 PWA 界面（仓库无前端测试基建，维持现状，手动验证）；真实公网链路端到端不自动化。

## Out of Scope

- 系统级推送（Web Push）——v1 只做应用内实时更新。
- 多设备拓扑（N 桌面端 / N 手机）——v1 固定 1×1，新配对顶旧。
- 应用层端到端加密——自托管 + TLS 下收益与威胁模型不匹配（见 ADR 0001），留待公共实例议题重启时再议。
- 官方公共中转实例。
- 裸 shell pane 的可见与驱动、从移动端启动新 AI 会话、远程执行任意 shell 命令。
- 终端原始输出镜像（含 ANSI 的文本流）。
- 中转存储转发 / 指令持久化排队。
- 桌面端本地 prompt 队列功能（另行立项）。
- SSH MCP 的 HTTP 传输与 WSL 可用性探索（独立进行中的议题，与本体系无协议耦合）。

## Further Notes

- Phase 0 与 Phase 1 必须分开发版：Phase 0 是独立 commit 并单独出 release，不等 Phase 1。
- iOS 上 PWA 需"添加到主屏幕"才有独立窗口体验；因 v1 无推送，iOS 的 Web Push 限制暂不构成影响。
- 中转服务器版本与桌面端版本可能漂移：协议消息应带版本号字段，两端在握手时校验，不匹配时给出明确升级提示（实现细节由开发者定，原则是"不静默错乱"）。
- 后续增强的自然路径（均已在共识中预留）：Web Push 完成通知、多桌面端拓扑、公共实例 + E2E。
