## 设计决议

**配置字段：`AppConfig::orchestrator_session_cap: Option<u32>`**（camelCase 落 `config.db` 的 settings 键，**没碰 `config.json` 投影**——那是给三个 sidecar 读的 SSH 投影，形状受 `mt_core::config_reader::ConfigSshView` 对账约束，与编排上限无关）。

- `None` 的语义是「**用户没设过**」而不是 0。默认值仍然只有 `mt_ai::DEFAULT_SESSION_CAP` 那一处——`mt-config` 不认识 `mt-ai`（也不该认识），所以兜底落在界面层的 `mt_app::orchestrator::resolve_session_cap`，与 `tray_max_projects` 同一个套路；
- `skip_serializing_if = "Option::is_none"`：没设过就不落键，配置文件保持干净；存量 `config.db` 里根本没有这个键，`serde(default)` 让它解析成 `None`——**这就是迁移路径**，不需要写迁移代码。反过来说，漏掉 `default` 会让老配置整份解析失败、连带项目列表一起丢，所以那一档单独有断言。

**取值范围 `0..=20`，下界刻意是 0。**

- **0 是合法值，语义是「暂停一切新的受编排会话」**（`ControlPlane::set_session_cap` 的文档口径本来就这么写）。允许它的理由是它比现有替代品好用：想临时停掉编排，另一条路是逐条去 AI 启动器上取消「允许编排」勾选，改完还得再逐条勾回来。而 0 这一档的行为是**明确的**——编排者收到 `sessionLimitReached`（429）而不是静默失败，ADR 0003 要的「不静默排队」在这一档照样成立。已经在跑的受编排会话不受影响（同下条）。
- **上界 20 不是防手滑，是防把机器拖垮**：一个受编排会话 = 一条 PTY + 一个几百 MB 的 agent 进程 + 它自己拉起的子进程。另有一条硬约束：上界必须 ≤ `mt_ai::MAX_SESSIONS_PER_ORCHESTRATOR`（每编排者记账表长度上限 50）——记账装不下全部**活着**的乐手时，工单 03 那条「修剪只丢已关的、活着的一条都不能丢」的不变式就被逼到墙角了。为此把那个常量**公开出去**，`上限的上界不超过记账表长度` 拿两侧真常量比，不是抄字面量（与 03 把 `ACTION_TIMEOUT` ↔ CLI `READ_TIMEOUT` 钉死同一个手法）。
- 越界值仍然钳回范围：`config.db` 是本程序自己写的，理论上填不进越界值，但配置也可能是从旧 `config.json` 迁进来的，钳一下比信它便宜。

**即时生效走专用 setter，不搭防抖那班车。** `AppStore::set_orchestrator_session_cap` 改完**当场**调 `ControlPlane::set_session_cap`（那是个 `AtomicUsize`），落盘照旧 `save_config_soon`（500ms 防抖）。两件事分开的理由：验收口径是「用户改完立刻在编排者里试」，而裁决读的是控制面那个原子量、不是磁盘——挂在 `save_config_now` 上就要多等半秒。这也正是 `patch_config` 的文档说的「需要额外副作用的那几项各有自己的 setter」那一档。

工单 02 留档的「500ms 防抖滞后」在本票**不构成问题**：这是个 `number_row` 草稿行（失焦 / 回车才提交一次），不是滑块，压根不存在拖动时每帧落盘的形态。

`AiBridge::refresh_orchestrator_mirror` **顺带也推一次上限**（镜像与上限同一班车）：它是「把配置刷进控制面」的唯一入口，启动接线（`store/mod.rs`）与每次落盘（`save_config_now`）都经过它，于是「盘上那份上限在开机时就接上」与「配置若由别的路径整体换掉（重读 / 迁移）也跟得上」两件事不必各自记得调一次。两条路径写的是同一个原子量，不存在先后打架。

**设置页落点是「AI Hook 事件」页新增的「编排」一节**，不另开一页：

- 控制端点 `/control/*` 就长在那个 hook 服务器的监听上（`hook_server.rs` 的 `try_handle_control`），**服务器没开时编排 CLI 一个命令都递不进来**。把这条依赖摆在同一页上，比让用户去两个地方找它诚实；
- 为一个数字新开一个 `SettingsPage` 要动 `ALL_PAGES` / `MENU_GROUPS` / `label_key` / 深链 id 表，收益不抵;
- 复用既有 `number_row`（草稿态、失焦或回车归一提交、归一后回写输入框），没为一个数字新造交互；
- **不随 hook 服务器开关置灰**：这是条持久化配置，关着服务器也该改得动（改完下次开起来就是新上限），依赖关系由页脚那句话说清。

**「调低不杀已存活」是天然成立的，但仍然上钉子。** 上限只在 `start_session` 那一行被读一次，所以调低天然不动已存活的乐手——正因为是天然的，才更容易被后来人一条「超限就回收」的顺手逻辑破掉（乐手 pane 里可能躺着改到一半的代码，ADR 0003 否决「编排者退出时自动关闭其受编排会话」用的是同一条理由）。`调低上限不动已存活的乐手` 断言三件事：调低后 `list-panes` 仍列出全部三个且 `alive`；桌面侧的死活现场一个字没改（控制面**压根没有**「关 pane」这个能力，真要加得先给 `OrchestratorActions` 开一道口子）；只有后续 `start-session` 吃到 429。

**文案与术语。** 新增 4 条进 `crates/mt-i18n/locales/settings.ts` 的 `aiHook` 段（双语，`846 → 850`），生成器重跑、`dict.rs` 一个字没手改。用户可见面按 `CONTEXT.md` 的术语纪律一律「受编排会话 / orchestrated session」，`上限文案与取值范围对得上` 双语各查一遍别名，顺带把「说明里手写的 `0~20`」与 `SESSION_CAP_MAX` 对上——改了常量忘了改文案会在那儿红。

## 留档（未整改）

- **取值范围在文案里是手写的**（中文「（0~20）」/ 英文「(0-20)」）。正规做法是 `tr!` 带参数，但那要给 `number_row` 加一条「说明可带参数」的口子（现有 5 个调用点全是静态 key），为一处插值改公共小件不划算。当前拿 `上限文案与取值范围对得上` 这条测试兜住漂移：改了 `SESSION_CAP_MAX` 忘改文案就红。
- **上限是「每编排者各算各的」，不是全局并发闸**。裁决是 `live_session_count(grant.pane_id) >= session_cap()`（工单 03 的 `名额按编排者各算各的` 钉着这条），所以同时开三个编排者、上限设 5 时，桌面上最多能有 15 个受编排会话。设置页的文案写的是「一个编排者同时最多能有几个」，没有撒谎，但用户可能按「总数」理解。要不要再加一道全局闸留给后续裁决——ADR 0003 只写了「同时存活的受编排会话有硬上限」，没说那是每编排者还是全局。
- **改上限不影响已经超限的现场，包括「超了多少」这件事本身不可见**。把上限从 5 调到 1 时，桌面上仍有 5 个受编排会话在跑，界面上没有任何地方提示「当前 5 / 上限 1」。编排者自己调一次 `list-panes` 就知道，用户不知道。工单 04 做 tab 的「受编排」出身标识时可以顺带定一条展示口径（比如设置页那行右边挂一个「当前 n 个在跑」）。
- **`0` 这一档没有额外的界面提示**。填 0 之后设置页看起来与填 5 没有区别，只有说明里那句「0 = 暂停新的受编排会话」在讲这件事；编排者那边拿到的是 `sessionLimitReached`（429），错误消息说的是「已达上限」而不是「被管理员暂停了」。判为可接受：错误码是闭集、语义没有撒谎，而为一档取值造一条专属错误码会让 CLI 的分档表变长。
- **上限改动不通知已经在等的请求**。`start-session` 是同步往返（3 秒时限），上限在请求飞行途中被改小时，这一趟按它读到的那一刻的值判——没有重试、没有回滚。窗口是毫秒级且结论无论如何都合法（要么起成要么 429），不值得为它加同步。
- **没做真机验证**（并行还有别的 agent 在跑，起 GPUI dev 实例会占 `target/debug` 的 exe）。设置行的渲染、`number_row` 的失焦提交、改完立刻在编排者里试这条端到端仍未在真窗口上走过，留工单 09 一并验收（与工单 02/03 的「CLI ↔ 真 hook server 的 HTTP 往返」同一批）。
