# 04 — 受编排标识与「编排者已离场」态

**Parent:** issue #61（编排者 Orchestrator MVP）

**What to build:** 受编排会话的桌面可辨识度。乐手 tab 带「受编排」出身标识，hover 可见是哪个编排者启动的；编排者退出（pane 关闭或 agent 退出）后，其乐手照常活着，标识降级为「编排者已离场」。出身不构成状态（与「移动端发起的会话」同构）：除标识外，乐手与普通 pane 无任何区别——用户随时可亲手接管、对话或关闭。

**Blocked by:** 03（乐手与范围记账先存在）

**Status:** done（实施提交见下方「设计决议」段末）

- [x] 乐手 tab 有出身标识，hover 显示编排者身份（展开态 tab 栏与最大化折叠条各一处，同一枚 `origin_badge`）
- [x] 编排者退出后乐手不死，标识转「编排者已离场」（`revoke_pane` 由「删记账」改成「留记账 + 置已离场位」）
- [x] MVP 无收养：编排者 pane 重启为新身份，前世乐手保持已离场态（撤销与**重复授予**两条路都置位）
- [x] 新文案进 i18n 字典源头并重跑生成器（`locales/paneGroup.ts` + `gen_from_ts.mjs`，对账常量 846 → 849）
- [x] `cargo test --workspace` / sidecars 工作区测试 / sidecars 构建三条全绿

## 设计决议

### `revoke_pane` 的新语义：出身留着，可达性收走

工单 03 那一版编排者退场时把**名下记账整体删掉**（`retain` 掉 `orchestrator_pane_id == pane_id` 的全部条目）。出身信息随之消失，「编排者已离场」就无从显示——本票的核心就是把这一路改掉。现在两路各走各的：

| 谁关掉了 | 做什么 |
|----------|--------|
| **编排者**（`TokenRegistry::depart`） | 名下**还活着**的乐手记账留下，置 `orchestrator_departed`；已经关掉的那些**就地回收** |
| **乐手** | 记账留下，`closed` 里记一笔（供修剪挑「可以丢的那些」）。**例外**：它的编排者已经离场了 → 就地回收 |

可达性由 `OrchestratedSession::belongs_to(orchestrator_pane_id)` 一处收口——**pane 编号对得上 且 没离场过**，`list-panes`（`sessions_of`）/ 名额（`session_ids_of`）/ 点名（`resolve_target`）/ 修剪（`trim`）四处同时改判。工单要求守的三条：

1. **已离场编排者的前世乐手不许被任何人驱动**。原编排者的令牌在 `revoke_pane` 第一行就撤了，没人认证得成它；`belongs_to` 那个已离场位是给「同一编号上又拿到一次授予」准备的第二道闸——PTY 编号单调递增（`AppStore::next_pty_id` 只加不减），正常路径碰不到，但 `grant()` 明确支持「同一 pane 重复授予」（PTY 重开 / SSH 重连），少了这一位前世乐手会被今生认领。三条路（原令牌 / 重开的新身份 / 别的编排者）各一条断言，在 `已离场编排者的乐手谁也够不到`。
2. **名额判定不受影响**。`live_session_count` 走 `session_ids_of`，已离场的一条都不数：重开的编排者拿到的是满额（`已离场的记账不占名额` 把 cap 打满、离场、重开、再打满走了一遍）。
3. **修剪照顾到新增的已离场记账**。`trim` 同样只数当前身份名下的（否则前世那 50 条会把今生的额度吃光）。**已离场记账的回收口径**：等它那个乐手 pane 自己关掉——那一刻它既没有 tab 可标（pane 没了）也没有编排者读得到，`revoke_pane` 就地删掉。反过来（乐手先关、编排者后走）由 `depart` 里那次 `closed.remove` 兜住。于是**已离场记账只可能对着还活着的受编排 pane**，条数恒不超过桌面上活着的 pane 数，不是一条只涨不消的表；两种顺序各一条测试。

`grant()` 也调一次 `depart(pane_id)`：重复授予即新身份，这条与撤销那条是同一句话，落在同一个函数上。

### 出身怎么走到渲染路径

- **查询是只读的小值类型**：`ControlPlane::origins() -> HashMap<u32, SessionOrigin>`，`SessionOrigin` 只有「编排者叫什么」+「他还在不在」两个字段。`OrchestratedSession` 的项目/启动器那几样是给编排者看的，不进渲染路径。
- **不在每帧渲染里抢 `registry` 那把锁**（HTTP 线程也在用它）：`ControlPlane` 加一个 `origins_version: AtomicU64`，记账每变一次 `bump_origins()` 一下；`TerminalArea` 照 `layout_snapshot` 的老规矩缓存一份，号没变的帧只花一次原子读。维护点只有 `render` 开头那一句 `sync_session_origins`。
  ⚠️ 用法有顺序要求：**先读号、再取快照**。反过来会把旧快照配上新号存住、之后永远刷不掉；按正序最坏是紧挨着变更的那一帧多刷一次。这条写进了 `origins_version` 的文档注释。
- **编排者的名字在落地那一刻抄一份**（`StartSessionSpec::landed(pane_id, orchestrator_label)`）。控制面认不出（它不认识布局树），而**离场之后那个 pane 就没了，现查只会查到空**——「编排者已离场（Claude）」这句话只能靠落地时的快照。桌面侧用新加的 `AppStore::pane_label_by_pty`（跨项目，因为编排者可以在同分组的别的项目里起会话）取 tab 上那个统一口径的显示名（自定义名 > 远程连接名 > shell 名）。查不到传空串，展示侧兜「未知编排者」。

被否掉的两条：① 把出身写进 `PaneState`——「已离场」会随编排者关闭而变，那就成了事件驱动的第二份真相，与「记账住在控制服务」的 ADR 0003 口径打架，且 pane 关闭那条通知链本来就是本仓踩过坑的地方；② 渲染时现查编排者 pane 的标题——离场之后查不到，恰好是最需要它的时候。

### UI 落点

- **一枚 12px 图标**（`ICON_ORCHESTRATED`，一条拐下来的支线 + 箭头），挂在 tab 标题右侧、未读标左侧。**不用文字**：tab 最窄 110px，中文三个字挤掉标题，英文 "Orchestrated" 更不用想。
- **在场 info 蓝 / 离场 muted 灰 + 0.7 透明度**：不 hover 也看得出标识降过级（「降级」而不是「消失」——出身是既成事实）。
- **tooltip 挂在标识自己身上，不挂整条 tab**：挂整条的话鼠标停在 tab 任意处都弹，与悬停缩略图打架（同款理由见 `terminal_area.rs` 折叠条那处既有注释）。
- 展开态 tab 栏与**最大化折叠条**两处都画（折叠条那处的展示数据顺手从五元组改成具名的 `CollapsedTab`——五元组还读得过去，加上出身那一项就该给字段起名字了）。
- **出身不构成状态**：除这枚标识外一行没动。关闭、重命名、分屏、拖拽、恢复布局、亲手接管全照旧；标识**不落盘**（`SavedPane` 一个字没加——重启后 PTY 编号重新分配，记账本来就没了，MVP 无收养）。

### 术语纪律

用户可见面（tooltip 两句 + 兜底称呼）一律「受编排会话 / orchestrated session」，`origin_tooltip_in` 抽成不读全局语言的纯函数，**中英两种语言各一条断言**钉住「不许出现乐手 / musician」。「乐手」照旧只活在注释与测试名里（`CONTEXT.md` 的口语别名条款）。

## 留档（未整改）

- **标识的 tooltip 与悬停缩略图会同时出现**。tab 的缩略图认的是整条 tab 的 hover（展开态是非激活 tab，折叠条是每个 tab），鼠标停在标识上时两个浮层都会弹。判为可接受：标识是 12px 的精确目标，停在那儿就是在问出身；要让缩略图为它单独让路，得在标识的 `on_hover` 里与父元素的 enter/leave 到达顺序博弈（`terminal_area.rs` 里已有一处「离开分支必须核对是不是我们记着的那一个」的坑注释），代价大于收益。真机体感留工单 09，届时若碍眼，最省的改法是把出身那一行并进 `pane_preview::tab_preview_card`。
- **`AppStore::pane_label_by_pty` 没有单元测试**。本仓没有任何 `TestAppContext` / gpui 测试脚手架（全仓 grep 零命中），构造一个带 `project_states` 的 `AppStore` 需要新起一整套。它是 `ProjectState::pane_by_pty`（底下的 `SplitNode::pane_by_pty` 在 `tree.rs` 有测试）与既有 `pane_display_label` 的三行组合，风险面是「跨项目找不到」，由工单 09 的真机验收兜。
- **编排者的名字是落地那一刻的快照**。用户之后重命名编排者 tab，已经起好的乐手上显示的还是旧名字。修它要么现查（离场之后就查不到，等于放弃「已离场（某某）」）、要么在重命名时反向刷一遍记账（给 pane 重命名这条冷路径挂上编排控制面的依赖）。判为不值：出身说的本来就是「起它的时候那个人叫什么」。
- **`revoke_pane` 每次都做一遍 O(记账数) 的扫描**。它是每个 pane 关闭都会走的路径，而 `depart` 要遍历 `sessions` 找名下的条目。记账每编排者上限 50，pane 关闭是人手频次，判为无需索引。真要优化就加一张 `orchestrator_pane_id → Vec<pane_id>` 的反向索引，但那是第二份要同步的事实。
- **`origins()` 会带出「已关掉的乐手」那些条目**（编排者还在、乐手关了）。桌面上没有对应的 tab，查不到就是不画，无害；不为它单独过滤是因为过滤要问 `pane_liveness`，而那是注入进来的 trait——持 `registry` 锁时绝不调它（模块注释的铁律）。
- **`alive` 与出身回收都依赖 `AiPerception::pane_closed` 这条路径**（工单 03 已留档的同一条，本票加深了它的分量）：pane 关闭时若哪天不再调它，已离场记账也跟着回收不掉。当前 `AiBridge::remove_pane` 仍是唯一注销点，与令牌撤销同一处，自洽。
- **`list-panes` 会列出已关的乐手**（工单 03 留档）：本票没有加展示侧折叠口径——那是 CLI 输出的事，而本票只碰桌面标识。留给工单 05~07 定 CLI 输出格式时一并处理。
- **CLI ↔ 真 hook server 的整条 HTTP 往返仍未真机走过**（与 02 / 03 同一条），留工单 09。
