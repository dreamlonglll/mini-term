# 移除 cc-connect 集成，自研"移动端 + 自托管中转"远程驱动体系

mini-term 此前通过集成上游 cc-connect（IM 平台桥接）实现远程驱动 AI agent，但该路径依赖第三方进程管理、IM 平台配置和 cc-connect 自身的 agent 会话模型，与"AI 交互始终发生在 mini-term 桌面端"的定位不符。决定整体移除 cc-connect 集成（先行独立移除，不等替代品上线），改为自研三件套：自托管中转服务器（Rust axum，Docker 部署，消息不落盘、日志不记明文）+ 中转托管的 PWA 移动端 + 桌面端出站长连。移动端只收发消息，所有真实 AI/PTY 交互由桌面端代为执行。

## 关键边界（v1 的明确"不做"）

- 对话镜像数据源是会话记录（JSONL）解析，**不是**终端原始输出。
- 移动端只可见、可驱动处于 AI 会话中的 pane；裸 shell 不可见，不能远程执行任意 shell 命令，不能远程启动新 AI 会话。
- 移动端指令直接写穿 PTY（等价远程敲键盘），不做桌面端排队。
- 桌面端离线即拒收指令，不做中转存储转发（桌面离线 = PTY/AI 会话已死，补送无意义）。
- 拓扑 1×1（一中转一桌面一手机，新配对顶旧配对）；扫码配对 + 全链路 TLS，不做应用层 E2E（PWA 由中转托管，恶意中转可下发恶意 JS，应用层 E2E 在此威胁模型下是伪防护）；v1 无系统推送。

## 被否决的备选

- 保留 cc-connect 与新体系并存 / 同版本替换：两套远程体系共存徒增 UI、配置与测试面。
- 终端文本镜像 / 全 pane 可驱动：ANSI 噪音阅读体验差；裸 shell 可写等于把整机 shell 暴露到公网，威胁等级完全不同。
- 官方公共中转实例：独立开发者承担长期服务器成本、滥用防护与隐私责任，暂不做。
- 内网直连 / Tailscale：不满足移动网络下"出门在外"场景。
