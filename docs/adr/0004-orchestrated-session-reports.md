# 受编排会话的结果以「汇报」推送给编排者，投递方式是写穿编排者终端

ADR 0003 走通的是**拉**模型：编排者 `wait` 之后自己 `read-transcript` / `read-screen` 去判断结果。工单 09 真机验收暴露了两条软肋：hook 状态没有回合概念，「这一回合干完了」的判据只能写在 Skill 里靠编排者 LLM 自觉执行（send 后立刻 wait 拿到的是上一回合的 ai-idle）；每一步都要编排者主动轮询，它等待期间什么都干不了。本决定把方向反过来：**桌面端在受编排会话每个回合结束、停下等人、退出或被关、派活未被接收时生成一条汇报，以写穿编排者终端的方式送达**——等价于用户在编排者的 pane 里对它说了一句话，编排者因此开始新一轮。编排者不再阻塞、不再轮询。

## 关键边界

- **投递闸**：只在编排者 `ai-idle` 且成因不是 attention 时写入。编排者忙（ai-working）时暂存，回合结束后把积压的汇报合成一条投；编排者停在黄灯时不投（写入等于替用户代答，ADR 0003 铁律）；编排者退回裸 shell 时不投（粘贴会落进 shell）。暂存有上限，编排者 pane 关闭后暂存作废。
- **汇报由桌面端机械生成，不依赖受编排会话配合**：正文是该回合的会话记录增量（无记录的 agent 用画面尾部代替），附结束成因（`Stop` / `Interrupt` / `Stall`…原文）与涉及的任务编号。派活时桌面端在 prompt 尾部追加一段固定的汇报格式要求（结果 / 改动 / 验证 / 未完成；有不确定的事用文字提出并结束回合），让自述更规整；设置可关。
- **任务只是派活回执的身份，不与回合一一对应**：桌面端不承诺哪条 prompt 对应哪一回合，只判定一件事——写入之后受编排会话有没有开始处理新输入；超时未开始视为「未被接收」并汇报。
- **`send` 维持立即写穿**（与移动端指令同口径），新增黄灯拦截：目标停在等人处理时拒绝写入。
- **每个回合都汇报，不区分谁触发**：用户亲手接管受编排会话聊的那一回合同样汇报，编排者据此不会拿着过时认知继续派活。
- **受编排会话向编排者提问的正当方式是文字提问并结束回合**：问题随汇报送达，编排者可以作答。权限审批与交互式提问（弹选项菜单）仍归人处理，编排者不代答——ADR 0003 那条铁律一字不动。
- **不加新命令、零新 UI**：编排者「随时要求汇报」只靠 `send` 问它；不做 `status`；不做「终止 / 打断」；`wait` / `read-*` 原样保留降为备用手段。

## 被否决的备选

- **编排者阻塞在一条 `inbox --wait` 上等汇报**（像 Claude Code 的 Agent 工具）：编排者等待期间什么都干不了，与「随时插入新任务」相抵；而且那仍是拉。
- **桌面端替受编排会话排队派活，空闲才写**：更稳、agent 无关，但用户明确不要任务与回合一一对应，只要子 agent 正常按需响应输入即可；依赖各家 agent 自己的输入排队（Claude / Codex 有，Grok 未验）是接受的代价。
- **立即写穿编排者、不看它的状态**（与移动端指令同口径）：编排者停在审批提示时，一条汇报就是一次代答。
- **只汇报编排者写入之后的回合**：用户接管对编排者不可见，它会基于过时状态派活；且「这一回合是谁触发的」在 transcript 里无从区分，只能估，会误标。
- **新增 `status` 命令给机械快照**：用户判断只靠 `send` 问即可，少一套语义。
- **让受编排会话自己写汇报（只靠 Skill 教）**：回到靠 LLM 自觉；机械生成为底、格式要求为辅才两层都不靠自觉。

## 后果

- 汇报在编排者的对话里是 user 消息；用户正在那个 pane 打字的一瞬撞上投递，粘贴会插进去。先接受，真碰到再加「空闲满 N 秒才投」的设置。
- 「说完了」不等于「做对了」：汇报仍是受编排会话的自述，transcript 里没有工具调用与命令输出。编排者该验证的仍需自己跑测试或看 diff。
- 投递闸建立在编排者的黄灯判定之上，黄灯全链路（受编排会话挂黄灯 → 汇报 → 人处理 → 恢复后终态汇报）必须真机跑通，工单 09 留档的这一条不能再留。
