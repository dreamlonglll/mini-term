# 受编排会话的结果由桌面端生成「汇报」落成文件，编排者用 `wait` 取件、自己读正文

ADR 0003 走通的是**拉**模型：编排者 `wait` 之后自己 `read-transcript` / `read-screen` 去判断结果。工单 09 真机验收暴露了一条软肋：hook 状态没有回合概念，「这一回合干完了」的判据只能写在 Skill 里靠编排者 LLM 自觉执行（send 后立刻 wait 拿到的是上一回合的 ai-idle）。本决定把**事实**的生产搬到桌面端：**受编排会话每个回合结束、停下等人、退出或被关、派活未被接收时，桌面端生成一条汇报，正文落成编排者项目目录下的一个文件**；编排者仍然自己来取——`wait` 改为等待**汇报**而不是等待状态，有新汇报就返回一行「哪个会话、什么事、文件在哪」，正文由编排者用自己的 Read 工具按需读取。

首版曾把整段汇报正文写穿进编排者终端（等价用户对它说了一句话）。真机一看就否了：那段文字在编排者的对话里**长得像用户在输入**，容易被当成用户发言去回复；而且每条汇报都整段进上下文，编排者的上下文随派活次数线性膨胀。落文件 + 取件解决这两条：终端里一个字都不写，编排者只在自己决定要看时读文件，读多少由它定。

## 关键边界

- **什么都不写进编排者的终端。** 汇报的存在只通过 `wait` 的回执告知；编排者不阻塞时对汇报一无所知，这是它自己的选择。
- **`wait` 等的是汇报，不是状态。** `wait [--pane N] [--timeout S]` 阻塞到编排者名下有新汇报（可按受编排会话过滤）即返回并**取走**它们（取一次即收敛）；超时返回 `pending`。「拿到上一回合」的毛病因此消失——汇报是回合事件，不是快照。
- **汇报文件住在编排者所在项目的 `.mini-term/reports/<编排者 pane>/` 下**，一条一个文件，与 Skill 投放同一套 `.gitignore` 机制；编排者 pane 关闭时整目录删除。项目目录不可用时退到应用数据目录。
- **汇报由桌面端机械生成，不依赖受编排会话配合**：正文是该回合的会话记录增量（无记录的 agent 或增量为空时用画面尾部代替），附结束成因原文与涉及的任务编号。派活时桌面端在 prompt 尾部追加一段固定的汇报格式要求（结果 / 改动 / 验证 / 未完成；有不确定的事用文字提出并结束回合），设置可关。
- **任务只是派活回执的身份，不与回合一一对应**：桌面端只判定「写入之后受编排会话有没有开始处理新输入」，超时未开始视为「未被接收」并汇报。
- **`send` 维持立即写穿**，新增黄灯拦截：目标停在等人处理时拒绝写入。
- **每个回合都汇报，不区分谁触发**（用户接管受编排会话聊的那一回合同样汇报）。
- **受编排会话向编排者提问的正当方式是文字提问并结束回合**：问题随汇报落文件，编排者可以作答。权限审批与交互式提问仍归人处理，编排者不代答——ADR 0003 那条铁律一字不动。
- **不加新命令、零新 UI**：「随时要求汇报」只靠 `send` 问它；不做「终止 / 打断」；`read-*` 原样保留。

## 被否决的备选

- **整段汇报正文写穿进编排者终端**（首版，已实施后推翻）：像用户在输入，且上下文线性膨胀。
- **终端里只写一行「有新汇报，去读文件」的通知**：仍是一条假的用户输入，问题只是变小；用户明确要求终端里什么都不写。
- **桌面端替受编排会话排队派活、空闲才写**：用户明确不要任务与回合一一对应，只要子 agent 正常按需响应输入即可。
- **只汇报编排者写入之后的回合**：用户接管对编排者不可见，它会基于过时状态派活。
- **新增 `status` 命令给机械快照**：`send` 问它即可。
- **让受编排会话自己写汇报（只靠 Skill 教）**：回到靠 LLM 自觉；机械生成为底、格式要求为辅才两层都不靠自觉。

## 后果

- 编排者必须主动 `wait` 才知道有事发生。Skill 教它：派完活就 `wait`，`pending` 就再 `wait`；它想先干别的也行，回头再取，汇报不会丢（收件箱有上限，溢出丢最旧并计数）。
- 「说完了」不等于「做对了」：汇报仍是受编排会话的自述，文件里没有工具调用与命令输出。编排者该验证的仍需自己跑测试或看 diff。
- 项目目录里多一个 `.mini-term/reports/` 目录（已 gitignore），编排者关掉即清。
